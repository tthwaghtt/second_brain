# 문서가 서로 어긋나지 않게: 결정의 생애, 낡은 것 치우기, 맥락의 흐름

> 날짜: 2026-10-16 · 출처: MAGNUM OPUS 10-15~16 + 외부 조사(아래 10장) · 근거: 경험 + 측정(외부 연구) + 추정(표시함) · 태그: 모순, 겹침, 오염, 결정, 프롬프트, 인수인계
>
> **이 저장소에서 가장 중요한 노트(사용자 지정, 10-16).** 세션을 갈아타며 일할 때 품질을 가장 크게 망치는 것은 "틀린 정보"보다 "**맞았던 정보가 낡은 채 남은 것**"이다.

## 1. 왜 이게 가장 위험한가

- **낡은 결정은 "그럴듯한 오답"이다.** Chroma의 긴 입력 연구(18개 모델)에서 정답과 닮은 오답(distractor)은 **단 하나만 있어도** 성능을 떨어뜨렸고, 여럿이면 더 떨어졌다. 낡은 시작 프롬프트, "적용 대기"로 남은 줄, 옛 숫자가 바로 이 오답 역할을 한다. (측정, 외부)
- **같은 연구에서 질문과 정답이 덜 닮을수록, 입력이 길수록 더 빨리 무너졌다.** 장황한 문서는 그 자체로 위험을 키운다. (측정, 외부)
- **Claude Code 공식 문서:** 규칙끼리 모순되면 Claude가 **어느 쪽이든 임의로** 고를 수 있다. 그래서 규칙 파일은 200줄 아래로, 주기적으로 모순을 점검하라고 권한다. (외부 문서)
- **Anthropic의 맥락 설계 글:** 맥락은 "주의 예산(attention budget)"을 쓰는 유한 자원이다. 토큰마다 자리를 정당화해야 하고, 늘 싣는 것은 안정적인 핵심만, 나머지는 필요할 때 도구로 가져온다(just-in-time). (외부 문서)
- **이 프로젝트에서 실제로 생긴 일 (경험):**

| 무엇이 어긋났나 | 원인 | 지금의 막는 법 |
|---|---|---|
| 종탑 완공 시각이 문서마다 30.5 / 30.3 / 31.2초 | 코드로 계산하지 않고, 같은 값을 여러 문서에 따로 씀 | 숫자는 코드로 확인, 값은 한 문서에만 |
| 엔딩 복귀 각도를 `α+180°`로 씀 | 코드의 방위 규칙을 확인하지 않음 | 계획의 정정 장(0-3)에 "코드와 대조" |
| S2 시작 프롬프트가 로드맵과 상태 문서 두 곳에, 세 번 고쳐 씀 | 미래 세션의 프롬프트를 미리 18개 써 둠 | 프롬프트는 상태 문서 한 곳(5장) |
| 승인 뒤에도 문서 머리에 "적용 대기, '적용해 줘'라고 하면…"이 남음 | 결정이 닫힐 때 그 결정을 기다리던 문장을 찾아 지우지 않음 | 닫힌 결정의 문구를 검사 목록에 추가(6장) |
| "열린 결정" 목록이 두 문서에서 서로 다름 | 같은 목록을 두 곳에 둠 | 한 곳(설계 문서 10장)만, 상태 문서는 가리키기 |
| "레터박스"가 한 문서에선 화면 비율, 다른 문서에선 검은 띠 | 용어 표류(terminology drift) | 결정 때 용어를 바꾸고 전체 검색 |
| 옛 모순 검토 표가 지금 상태처럼 읽힘 | 날짜 붙은 기록과 현재 상태가 같은 꼴 | 기록은 그대로 두고 "지금" 열을 따로 |
| 문서 검사기가 날짜(10-10)를 장 번호로 읽음 | 검사기도 틀릴 수 있음 | 검사기는 일부러 망가뜨린 사본으로 시험 |

## 2. 문서를 "고치는 법"으로 네 종류로 나눈다

Diátaxis가 문서를 "한 문서는 한 종류만"으로 나누듯, 맥락 문서는 **어떻게 고쳐지는가**로 나눈다. 종류가 섞이면 낡은 것이 남는다. (외부 원칙 + 경험)

| 종류 | 고치는 법 | 예 (MAGNUM OPUS) | 외부의 같은 생각 |
|---|---|---|---|
| **흐름 (덮어씀)** | 매번 새로 씀. 옛 내용은 남기지 않음 | `STATUS.md`(지금, 다음 세션, 시작 프롬프트) | Cline 메모리 뱅크의 `activeContext.md`(가장 자주 바뀜, 세션마다 갱신) |
| **기준 (고쳐 씀, 날짜와 함께)** | 결정이 바뀌면 그 자리를 고치고 바뀐 날짜를 적음. 한 사실은 여기 한 곳 | `DESIGN.md`, 계획서 | spec-kit의 constitution(고칠 때 버전을 올리고 무엇이 바뀌었는지 보고) |
| **기록 (덧붙이기만)** | 절대 고치지 않음. 끝에 날짜와 함께 덧붙임 | `USER_DIRECTIONS.md`(사용자 원문) | ADR(결정 기록): 확정된 기록은 고치지 않고 새 기록이 "대체"함 |
| **보고서 (얼림)** | 그날의 결과로 얼림. 틀린 곳은 머리에 "정정 메모"만 | 조사 보고서 | 논문의 정오표 |

- 한 문서 안에 두 종류가 섞이면(예: 상태 문서 안에 결정 표 복사본) 반드시 한쪽이 낡는다. **복사본은 "가리키기 한 줄"로 바꾼다.**
- 늘 실리는 규칙 파일(`CLAUDE.md`)의 요약은 예외로 허용하되 "요약, 기준은 X"라고 밝히고 짧게. (경험)

## 3. 결정의 생애: 제안 → 확정 → 적용 → 대체

ADR(Architecture Decision Record)의 방식이 가장 단단하다. (외부: Fowler, adr-tools 코드)
- 결정은 **번호**가 있고, 확정되면 **고치지 않는다.** 바뀌면 새 결정이 옛 결정을 "대체(Superseded)"하고, **양쪽에 서로를 가리키는 링크**를 쓴다(adr-tools의 `adr new -s`가 실제로 옛 기록에 "Superceded by", 새 기록에 "Supercedes"를 씀). 번호는 다시 쓰지 않는다.
- "대체"(뒤를 잇는 결정이 있음)와 "폐기"(그냥 없앰), "부분 수정"을 구분하는 프로젝트도 있다.

**우리 방식으로 옮기면** (경험 + 일부 추정):
1. 사용자 원문은 원문 기록에 날짜와 함께(기록 문서).
2. 결정은 설계 문서의 "정한 것" 목록에 날짜와 원문 위치를 붙여(기준 문서). 아직 정할 것은 같은 장의 "아직 정할 것" 표 **한 곳에만**.
3. 결정이 바뀌면: 옛 줄은 지우지 않고 `~~취소선~~ → 새 결정(날짜)`, 새 줄에는 "옛 결정 대체"라고 씀. (추정: 결정마다 D-번호를 붙이면 커밋·코드 주석까지 추적이 쉬워짐. 아직 안 해 봄)
4. **그 결정을 "기다리던" 문장을 모두 찾는다**("적용 대기", "사용자가 정함", "S1 보고 때"). 이것이 가장 자주 놓친 단계였다.

## 4. 바꿀 때마다: 영향 범위 먼저 (Sync Impact)

spec-kit은 constitution(원칙 문서)을 고칠 때마다 **버전을 올리고(큰 변경/추가/문구) "Sync Impact Report"**를 남긴다: 무엇이 바뀌었고, 무엇이 더해지고 빠졌는지, 남은 할 일. (외부: github/spec-kit `templates/commands/constitution.md`)

우리 절차 (경험):
1. 바꾸는 결정의 **낱말과 숫자**로 프로젝트 전체를 검색(`grep -rn "84.1\|레터박스\|적용 대기"`).
2. 나온 자리마다: 기준 문서면 고치고, 복사본이면 가리키기로 바꾸고, 기록·보고서면 그대로 둠(필요하면 정정 메모).
3. 보고에 "바꾼 곳 / 그대로 둔 곳(왜)"를 적는다.
4. 문서 검사 도구를 돌린다(6장).

## 5. 시작 프롬프트: 미리 만들지 않고, 한 곳에서만 갱신 (사용자 결정, 10-16)

**문제:** 미래 세션의 프롬프트를 로드맵에 미리 써 두면, 앞 세션의 결과가 바뀔 때마다 낡는다. 실제로 S2 프롬프트를 세 번 고쳐 썼고, 두 곳에 있어 어느 것을 붙여 넣을지 헷갈렸다. (경험)

**규칙:**
1. 로드맵에는 세션마다 **전제·목표·읽을 것·할 일·멈출 곳**만. 프롬프트는 두지 않는다. 그 세션만의 주의(예: "비용은 먼저 확인")는 "시작할 때" 한 줄로.
2. 다음 세션의 프롬프트는 **상태 문서 한 곳**("다음 세션 시작 프롬프트")에만. 머리에 **작성 날짜, 작성한 세션, 다음 세션 번호, 승인 근거**.
3. **마지막에만 쓰지 않는다.** 다음 할 일이 정해지거나 바뀌는 순간마다 고쳐 쓴다. 세션이 갑자기 끊겨도(토큰 한도, 오류) 맞는 프롬프트가 남게.
4. **승인 문구를 지어내지 않는다.** 프롬프트는 사용자가 붙여 넣는 "사용자의 말"이 되므로, 승인은 원문 기록에 날짜와 함께 있는 말만 인용한다. 사용자는 붙여 넣기 전에 읽는다.
5. 본 세션만 고친다(곁가지 세션이 덮어쓰지 않게).
6. 프롬프트가 없거나 낡았을 때(작성 날짜 < 상태 문서 갱신 날짜)를 위한 **비상용 공통 틀 하나**를 로드맵 1장에 둔다. 규칙 파일이 "상태 문서와 로드맵의 그 세션 항목을 읽어라"를 이미 말하므로 공통 틀로도 일이 된다.
7. 검사기가 확인: 프롬프트의 세션 번호 = 상태 문서의 "다음 세션" = 로드맵에 있는 세션, 작성 날짜 ≥ 상태 갱신 날짜, 로드맵에 세션별 프롬프트가 다시 생기지 않았는지.

이것은 "앞날은 목표만, 구체적인 글은 바로 다음 한 걸음만" 원칙의 한 예다. spec-kit도 안정적인 "무엇"(spec)과 유연한 "어떻게"(plan, tasks)를 나누고, 뒤의 것은 단계마다 새로 만든다. (외부 + 경험)

## 6. 기계로 막을 것과 사람(모델)이 볼 것

**결정적 검사 (매 세션 끝, 0개가 아니면 커밋하지 않음)** — MAGNUM OPUS `scripts/docs/doc_check.py`:
- 없는 장을 가리키는 참조, 없는 파일 경로(문서와 코드 속 문자열)
- 원본 데이터와 다른 숫자(편집표 원본 ↔ 설계 문서의 샷 길이)
- 코드 지도가 코드보다 오래됨
- **낡은 표현 목록:** 결정이 닫힐 때마다 그 결정을 기다리던 문구를 목록에 더함("적용 대기", "S1 보고 때"…). 날짜 붙은 기록 장과 보고서·원문은 제외. (한계: 목록에 없는 표현은 못 잡음)
- **시작 프롬프트 일관성**(5장 7번)
- 검사기 자체는 **일부러 망가뜨린 사본**으로 잡히는지 시험한다(실제로 날짜를 장으로 읽는 버그를 찾음).

외부의 같은 계열(외부, 성숙도 미확인): 문서와 그 문서가 설명하는 코드 파일을 해시로 묶어 코드가 바뀌면 문서를 표시하는 도구(Codocia), README와 실제 코드를 대조하는 도구(stale-cli), CI에서 병합 diff를 Claude에게 주고 문서 어긋남을 찾게 하는 방식.

**의미 점검 (결정이 크게 바뀐 뒤, 또는 몇 세션마다)** — spec-kit의 `analyze` 방식을 따름:
- **읽기만 한다.** 고치지 않고 보고서만. 고치기는 사용자 승인 뒤.
- 찾을 것: 겹침(같은 내용 두 곳), 모순(값이 다름), 낡은 표현(결정 뒤에 남은 미정 표현), **용어 표류**(같은 것을 다른 이름으로), 애매함.
- 심각도로 나눔: 다음 세션이 틀리게 일할 수 있으면 높음, 헷갈림 정도면 중간, 모양만이면 낮음. 원칙 문서(규칙 파일·사용자 원문)와 부딪히면 무조건 높음.
- 이 세션(10-16)에서 이렇게 해서 낡은 표현 7곳, 순수 복사본 4묶음, 열린 결정 목록 불일치를 찾았다. (경험)

## 7. 장황함과 오염 줄이기

- **늘 실리는 것은 작게:** 규칙 파일 200줄 아래(Claude Code 공식 권장), 메모리 색인은 한 줄 요약. 나머지는 장 단위로 필요할 때(just-in-time). (외부 + 측정: 278줄 → 161줄)
- **읽는 길에서 옛 기록을 뺀다:** 옛 문서는 보관 폴더로, 날짜 붙은 기록 장은 "그때의 기록"이라고 머리에 밝힘. 검사기도 그 장은 건너뜀.
- **정리의 네 동작**(Anthropic의 consolidate-memory 스킬): ① 오래 갈 것(선호, 작업 방식)과 날짜가 지난 것(끝난 일)을 가른다 ② 겹치는 것을 합친다 ③ "다음 주" 같은 말을 절대 날짜로 바꾼다 ④ 다시 찾기 쉬운 것은 지운다. 색인은 200줄·25KB 아래.
- **압축(compaction) 때 남길 것:** 결정, 풀리지 않은 문제, 구현 세부. 버릴 것: 되풀이된 도구 출력. (Anthropic) — 그래서 압축 전에 결정을 문서에 저장하고 커밋하는 규칙이 맞다.
- **구조가 깔끔해도 방심하지 않는다:** Chroma 연구에서 논리적으로 잘 짜인 긴 글이 오히려 찾기 어려웠다. 길이를 줄이는 것이 구조보다 먼저. (측정, 외부 — 해석은 추정)
- 사람만 볼 메모는 `<!-- -->` 주석(Claude Code가 싣지 않음).

## 8. 맥락이 한 줄로 흐르게

```
사용자 원문(기록, 덧붙이기만)
  → 결정(기준 문서, 날짜·원문 위치) → 적용 계획(기준, "초안" 값은 적용 때 재서 확정)
  → 상태(흐름, 매번 덮어씀) → 다음 세션 시작 프롬프트(상태 문서 안, 날짜·세션)
  → 새 세션: 규칙 파일(자동) → 상태 "지금" → 로드맵 그 세션 → "읽을 것"의 장만
```
- 각 고리는 앞 고리를 **가리킨다**(원문 날짜, 결정 위치). 내용을 베끼지 않는다.
- 새 세션은 이 길만 따라 읽는다. 다른 길(옛 보고서, 옛 표)은 일부러 열 때만.
- 세션을 넘어가는 때(→ `context-hygiene.md`): 목표를 끝냈을 때, 압축이 두 번째일 때, 결정을 잘못 기억하는 일이 보일 때.

## 9. 체크리스트

**결정이 바뀔 때:** 원문 기록에 덧붙임 → 기준 문서 고침(옛 결정은 취소선과 링크) → 그 낱말·숫자로 전체 검색 → 복사본은 가리키기로, "대기" 문구는 지움 → 낡은 표현 목록에 그 문구 추가 → 다음 세션 프롬프트에 영향 있으면 갱신.

**세션 끝:** 상태 문서 새로 씀(프롬프트 포함, 날짜·세션) → 문서 검사 0개 → 커밋 → 사용자에게 프롬프트 알림.

**몇 세션마다 또는 큰 변경 뒤:** 읽기만 하는 의미 점검(6장) → 보고 → 승인 뒤 정리 → 정리의 네 동작(7장).
