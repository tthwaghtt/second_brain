# lean-context: 필요한 것은 빠짐없이, 나머지는 열지 않는다

**왜:** 응답할 때마다 지금까지 읽은 것을 전부 다시 읽습니다. 관련 없는 문서 하나도 판단을 흐립니다. 반대로 필요한 것을 덜 읽으면 틀린 답을 내고, 다시 하느라 더 씁니다. 기준은 응답 하나의 토큰이 아니라 **일 하나를 끝내는 데 든 토큰**입니다.

## 1. 읽는 순서: 지도 → 찾기 → 장·범위 → 통째

1. **지도:** 규칙 파일의 찾아가기 표, INDEX, 코드 지도(있으면). 없으면 `find . -maxdepth 2 -not -path './.git*'`와 `wc -l`로 크기부터 봅니다.
2. **문서:** 장 목록부터 보고(`python3 <이 스킬 폴더>/scripts/doc_section.py <문서> --list`), 필요한 장을 **통째로** 꺼냅니다(`doc_section.py <문서> 3-2`). 장 단위로 읽으면 잘라 읽다 빠뜨리는 일이 없습니다.
3. **코드:** `grep -n`으로 자리를 찾고 그 범위만 읽습니다(Read의 offset/limit). 고칠 곳은 앞뒤를 넉넉히 읽습니다.
4. **통째로 읽기:** 짧은 파일(약 200줄 이하), 또는 그 파일 전체가 판단 근거일 때만.

## 2. 빠뜨리지 않는 법

- 판단이 걸린 곳은 **장 전체**를 읽습니다. grep으로 걸린 한 줄만 보고 결론 내지 않습니다.
- 숫자나 규칙을 대조할 때는 **양쪽 원본을 다** 엽니다(문서의 장 + 코드의 줄).
- 관련 있는지 모르겠으면 머리말, 장 목록, 첫 20줄만 보고 정합니다.
- **지금 결정에 필요한 것만 읽습니다.** 다음 단계나 다음 세션에 필요할 것 같은 장은 위치만 적어 두고 그때 엽니다.
- 같은 사실이 여러 곳에 있으면 날짜와 문서 종류(기록·기준·상태)로 무엇이 최신 기준인지 가립니다. 결정 기록처럼 날짜순으로 쌓이는 문서는 최신 항목부터 거꾸로 읽습니다.
- 읽지 않고 넘어간 것은 보고에 "확인 안 함"으로 적습니다.

## 3. 출력은 걸러서 받는다

- 긴 출력(테스트, 빌드, 로그)은 파일로 보내고 끝부분이나 오류만 받습니다: `cmd > /tmp/out.log 2>&1; tail -n 20 /tmp/out.log`, `grep -n -m 20 ERROR`.
- 세기, 모으기, 비교는 스크립트로 계산해서 답만 출력합니다. 파일 내용을 대화로 끌고 오지 않습니다. Read는 고칠 때와 정독이 필요할 때 씁니다.
- 방금 쓴 파일은 다시 읽지 않습니다. 이미지는 여러 장을 한 시트로 모아 봅니다.
- 열지 않는 곳: `node_modules`, 빌드·렌더 출력, 백업·보관 폴더(규칙 파일이 "따르지 말 것"이라 한 곳), 바이너리.

## 4. 하위 에이전트에 맡기기

- **맡길 때:** 여러 파일과 폴더를 훑어 결론만 필요할 때, 서로 독립인 일이 2~5개일 때.
- **맡기지 않을 때:** 파일 하나짜리 일, 이미 경로를 아는 일. 하위 에이전트도 토큰을 쓰고, 끝나면 이 세션을 다시 깨웁니다.
- **넘길 것:** 한 줄 맥락, 할 일, 읽을 파일 경로, 돌려받을 형식. 대화 내용을 붙여 넣지 말고 필요한 것은 파일로 줍니다.
- **돌려받을 것:** **15줄 이내 요약**. 자세한 내용은 파일로 받고 경로만 받습니다.
- **확인:** 결과를 바탕으로 무언가를 고치기 전에, 중요한 주장은 근거 줄을 직접 엽니다.

## 5. 코드 지도

코드 파일이 수십 개를 넘는 프로젝트에서는 `references/graphify.md`를 읽고 Graphify로 지도를 만듭니다. 그보다 작으면 쓰지 않습니다.

## 6. second_brain 원본 열기

second_brain 레포에서 `INDEX.md`만 먼저 읽고, 필요한 노트의 장 하나만 엽니다. `inbox/`는 읽지 않습니다.
