# plan-first: 만들기 전에 함께 정하고, 세션으로 쪼갠다

**왜:** 다시 만들기와 맥락 오염의 대부분은 "무엇을 원하는지 덜 안 채 만들기"와 "한 세션에 너무 많이 하기"에서 나옵니다. 기획에 쓰는 토큰은 다시 만드는 토큰보다 쌉니다. 다만 작은 일에 이 절차를 다 쓰면 그게 낭비입니다.

## 1. 크기부터 정한다 (첫 응답에 한 줄로 말함)

| 크기 | 알아보는 법 | 할 일 |
|---|---|---|
| 바로 | 요청에 필요한 것이 다 있고 되돌리기 쉬움 | 하고, 한 일을 말함 |
| 작음 | 한 세션 안, 정할 것 1~3개 | 채팅으로 "무엇을 / 어떻게 확인" 합의 → 함 |
| 프로젝트 | 여러 세션, 정할 것이 많음, 되돌리기 비쌈 | 2~5장 전부 |

사용자가 크기를 바꿀 수 있습니다. 하다가 커지면 멈추고 말한 뒤 한 단계 올립니다. 서로 독립인 프로젝트 여럿이면 순서를 정하고 하나씩 합니다.

## 2. 인터뷰 (프로젝트 크기)

- **첫 메시지는 짧게, 이 모양으로 씁니다(약 1,500자 이하).**
  1. 크기 한 줄과 그 이유
  2. "질문 없이 바로 시작하길 원하면 말해 줘" 한 줄
  3. 이해한 것 3~5줄. 추측은 "추측"이라고 표시
  4. 질문 4개 이하
  
  조사하다 발견한 문제는 **이번 일의 결정을 바꾸는 것만** 한 줄씩 적습니다. 나머지는 "설계 문서에 모아 둘게" 한 줄로 미룹니다. 사용자가 한 번에 읽고 답할 수 있어야 대화가 빨리 끝나고, 대화가 빨리 끝나야 맥락도 덜 씁니다.
- **첫 질문 전 조사는 질문을 잘 고르는 데 필요한 만큼만 합니다.** 규칙 파일과 상태 문서, 관련된 장 정도면 됩니다. 깊은 조사는 답을 받은 뒤 설계 문서를 쓸 때 합니다.
- **질문은 한 번에 1~4개**, 번호를 붙이고 질문마다 **내 추천 답**을 답니다. "응"이 곧 추천을 받아들이는 뜻이 되게 묻습니다. 선택지 도구(AskUserQuestion)가 있으면 추천을 첫 선택지에 둡니다.
- **사실 찾기는 내 일입니다.** 코드·문서·웹으로 알 수 있는 것은 묻지 말고 찾습니다(넓으면 하위 에이전트, `lean-context` 4장).
- **다룰 것 (대본 아님):** 왜 지금, 성공의 모습 / 목표, 안 할 것, 실패의 모습 / 이미 있는 것 / 만드는 수단(사용자가 정할지 나에게 맡길지) / 승인 지점, 건드리면 안 되는 것 / 잴 수 있는 완성 기준.
- **되짚기:** 한 부분을 이해할 때마다 200~300자로 말해 확인합니다. 내 추측은 "추측"이라고 표시합니다.
- **끝:** 남은 질문이 없고 사용자가 "맞다"고 할 때.

## 3. 설계 문서

- **어디에:** 프로젝트의 기준 문서(PRD, DESIGN 등 이미 있으면 그곳). 없으면 위치를 묻습니다.
- **틀:** `references/design-doc.md`. 사용자가 정한 것은 사용자 말 그대로, 내가 정한 것은 "내 판단"으로 표시합니다.
- **빌더 점검:** 하위 에이전트 하나에 `references/builder-check.md` 프롬프트로 문서를 읽힙니다. 돌아온 질문을 세 무더기로 나눕니다.
  - 이미 답이 있음 → 문서에 씀
  - 사소함 → 내가 정하고 "내 판단"으로 표시
  - 사용자만 답할 수 있음 → 한 메시지에 묶어 한 번만 물음
  
  하위 에이전트가 없으면 내가 그 빌더처럼 읽습니다.

## 4. 세션 계획

- **틀:** `references/session-plan.md`.
- **세션 하나 = 목표 하나 = 새 맥락 하나에 들어가는 크기.** 사람 확인이나 데이터를 기다리는 지점에서 끊습니다.
- **세션마다 적을 것:** 전제(앞 세션의 산출물) / 목표 / 읽을 것(파일 + 장, 꼭 필요한 것만) / 할 일 / 멈출 곳 / 완성 기준과 확인 방법.
- **시작 프롬프트는 미리 쓰지 않습니다.** 다음 세션 하나만 상태 문서에 씁니다(`session-handoff` 3장).
- "안 할 것"과 "아직 모르는 것" 목록을 함께 둡니다.

## 5. 승인 문

- **프로젝트 크기:** 사용자가 설계 문서와 세션 계획을 승인하기 전에는 만들지 않습니다. 만들기에는 코드, 뼈대(스캐폴딩), 설치, 파일 여러 개 만들기가 들어갑니다. 읽기와 조사는 괜찮습니다.
- 사용자가 질문을 건너뛰자고 하면 문은 없어집니다. 그때는 중요한 선택(플랫폼, 언어, 위치)을 한 줄로 말하고 시작합니다.
- 승인은 보여 준 것까지만 덮습니다. "좋아"는 아직 쓰지 않은 부분까지 승인한 것이 아닙니다.

## 6. 실행 중

- 계획에 없던 결정은 `판단: 무엇 — 왜 — 틀리면 드는 비용` 한 줄로 상태 문서에 남기고 계속합니다. 멈추고 묻는 건 되돌릴 수 없는 일, 보안, 바깥에 영향이 가는 일, 계획 자체가 깨졌을 때뿐입니다.
- "끝났다"는 증거(실행 결과, diff, 완성 기준 체크)와 함께만 말합니다.
