## 1. 의도와 왜

- **무엇:** 새 프로젝트를 시작할 때 부르는 스킬이다. 도하가 "이걸 만들고 싶다"고 하면 AI가 스펙 문서를 쓸 수 있을 때까지 질문한다(역프롬프트: 사람이 AI에게 프롬프트를 주는 대신, AI가 사람에게 물어 프롬프트를 만든다). 인터뷰가 끝나면 md 문서로 정리하고, 실제 만들기는 다른 세션이 한다.
- **왜(도하의 답 세 가지):**
  1. AI가 의도를 덜 알고 만들어서 다시 만든 적이 있다.
  2. 더 똑똑한 모델에 맞는 새 지침(6가지)을 새 프로젝트부터 적용하고 싶다.
  3. 도구와 디자인을 잘 몰라서 조사가 필요하다. 다만 같은 조사를 프로젝트마다 되풀이하지 않도록, 도하는 다른 프로젝트에 **조사 창고**(도구와 디자인 레퍼런스를 넓게 조사해 둔 곳)를 따로 만들 예정이다. 이 스킬은 그 창고에서 꺼내 쓴다.

## 2. 목표 / 안 할 것 / 실패의 모습

**목표**
- 인터뷰가 끝나면, 앞 대화를 모르는 새 세션이 스펙 문서만 읽고 도하에게 다시 묻지 않은 채 만들기를 시작할 수 있다.
- AI는 무엇을 만드는지뿐 아니라 왜 만드는지, 그리고 도하가 쓴 문장의 뜻(모호한 곳, 두 가지로 읽히는 곳)을 확인한다.
- 도구와 디자인 선택은 AI가 조사해 후보와 출처를 보여 주고, 고르는 건 도하가 한다.
- 새 프로젝트가 만드는 지침 문서(CLAUDE.md 등)를 6가지 지침으로 점검한다.

**안 할 것**
- 인터뷰하는 세션에서 만들기(코드, 뼈대, 설치)를 시작하지 않는다.
- AI가 점수를 매겨 골라 주는 식으로 도하의 판단을 대신하지 않는다(`insights/judgment-stays-human.md`).
- 조사 창고 자체를 만들지 않는다. 창고는 다른 프로젝트의 일이다.
- sorbh판에서 ~~스펙과 코드가 어긋났는지 검사하는 부분(VERIFY.md), 스펙 미리보기 디자인 틀(STYLE_PRESETS.md),~~ GitHub 이슈를 입력으로 받거나 스펙을 이슈에 올리는 부분은 가져오지 않는다. (2026-11-24 고침: 어긋남 검사와 미리보기는 2판에서 되돌렸다. 도하가 정함, 4장 21번. 미리보기 틀에서는 그림 종류와 페이지 짜임만 가져온다, 4장 32번)
- 기존 코드를 분석하는 부분(sorbh판의 코드 분석)은 가져오지 않는다. 이미 있는 프로젝트는 plan-first의 몫이다(2026-11-24).
- 창작물에만 해당하는 것(스토리보드, 장면 목록, 레퍼런스 보드 같은 창작물판 미리보기)은 2판에 넣지 않는다. 갈래 세션(이 스킬의 만들기 세션에서 갈라져 나와 두 원본과 견준 표를 만들고 창작물 쪽을 조사하는 세션)이 도하와 정한 뒤 따로 넘긴다(10장).
- 6가지 지침을 이 스킬 자체나 second_brain 전체에 적용하지 않는다(도하의 답: "새 프로젝트 문서에만").
- 세션 중간의 큰 일은 다루지 않는다. 그건 plan-first의 몫이다.

**실패의 모습(돌아가도 실패인 것)**
- 질문은 많이 했는데, 스펙을 받은 세션이 도하에게 다시 물어야 한다.
- 도하가 "알아서 해", "좋아요"라고 한 것을 결정으로 적는다.
- 도하가 혼자 답하기 어려운 기술 질문(예: 어떤 DB를 쓸지)을 후보와 설명 없이 묻는다.
- 같은 규칙이 plan-first와 이 스킬 두 곳에 생긴다.

## 3. 제약

- **위치:** 원본은 `~/MY_PROJECT/second_brain/skills/reverse-prompt/`, `~/.claude/skills/reverse-prompt`는 그 폴더로 가는 링크다(다른 스킬과 같은 방식).
- **만드는 도구:** `/anthropic-skills:skill-creator`.
- **공통 규칙(`~/.claude/CLAUDE.md`):** 도하에게 보이는 글은 한국어로, plain-words 스킬대로 쓴다. 돈이 드는 일과 되돌리기 어려운 일은 먼저 묻는다. 비밀값은 쓰지 않는다.
- **유료 도구:** 유료 조사 도구(Apify 등)와 유료 AI 호출은 쓰기 전마다 도하에게 묻는다.
- **라이선스:** 두 원본은 MIT다. 문장을 옮기지 않고 방식을 골라 한국어로 다시 쓰고, `skills/ATTRIBUTION.md`에 적는다.
- **질문 하나씩:** 질문 팝업(AskUserQuestion)에는 늘 질문 하나만 넣는다(도하의 답 "늘 하나씩"). 선택지는 2~4개, AI의 추측 답을 첫 선택지에 둔다. 도하는 기타 칸에 자유롭게 쓸 수 있다.

## 5. 스킬이 하는 일 (2판: 9단계)

> 2판(2026-11-24)에서 바뀐 곳은 "(2판)"으로 표시했다. 자세한 문장은 SKILL.md와 참고 파일이 기준이다.

### 5-1. 원문 읽기
- 도하의 요청(말 또는 파일)을 문장마다 나눠 표로 보여 준다: 문장 / AI가 읽은 뜻 / 모호한 곳(두 가지로 읽히면 두 뜻을 다) / 서로 부딪히는 곳 / 빠진 것.
- 표 위에 한 줄: "지금 이해: <한 문장>. 확신: 약 N%". 70%보다 낮으면 무엇을 몰라서인지 같은 줄에 붙인다(addyosmani판 1단계).
- 그 폴더에 코드나 문서가 이미 있는지 가볍게 본다. 아무것도 없는 새 프로젝트면 다룰 주제를 기술 선택, 구조, 데이터, 배포까지 넓힌다(sorbh판의 새 프로젝트 방식).
- 코드, 문서, 웹으로 알 수 있는 것은 묻지 않고 찾는다.

### 5-2. 의도 인터뷰
- 한 번에 질문 하나. 질문마다 AI의 추측 답과 그렇게 짐작한 이유를 붙인다. 도하는 처음부터 답을 지어내기보다 틀린 추측을 고치는 게 빠르다(addyosmani판 2단계). 도하가 맞장구만 치지 않도록, 가끔은 도하가 반대할 것 같은 쪽으로도 추측한다.
- 처음 다룰 것: 왜(가장 먼저), 누구를 위해, 성공의 모습, 안 할 것, 가장 강한 제약.
- 도하가 쓴 문장의 뜻을 묻는다: 왜 이 낱말을 썼는지, 이렇게 읽는 게 맞는지.
- "좋은 말처럼 들리는 답"(확장성, 깔끔하게, 요즘 방식, 남들처럼)이 나오면 "누구에게도 설명할 필요가 없다면, 진짜 원하는 건 뭐예요?"라고 묻는다(addyosmani판 3단계).
- **답을 받을 때마다 AI가 스스로 검사한다:** 앞 답과 부딪히는지, 모호한 말이 있는지, 규모에 비해 과하게 만들려는지, 빠진 경우가 있는지. 보이면 바로 짚고 묻는다(sorbh판의 반박). 도하가 반박에 동의하지 않으면 한두 번 더 묻고, 두 쪽 생각을 결정 표에 함께 남긴다.
- 개인정보, 로그인·권한, 비밀값, 지우지 않고 쌓이는 데이터처럼 보안 문제가 보이면, 도하가 답하거나 위험을 알고 받아들일 때까지 스펙을 쓰지 않는다(sorbh판 보안 막기 중 그 프로젝트에 해당하는 것).
- **(2판)** 답마다 다음 질문 앞에 "고친 이해: <한 문장>. 확신: 약 N%" 한 줄을 쓴다(addyosmani판 예시, 4장 20번).

### 5-3. 다룰 주제 목록
- `references/coverage.md`에 기본 주제와 프로젝트 종류에 따라 더할 주제를 둔다. 예: 기술 선택, 구조, 데이터, 배포와 운영, 디자인(UI, 모션, 사진, 영상, 소리, 글꼴과 색, 브랜드 등 그 프로젝트에 맞는 것), 비용, 비밀값과 개인정보, 법과 라이선스, 세션 크기, 승인 지점, 건드리면 안 되는 것. 목록은 대본이 아니다. 프로젝트에 맞게 늘이고 뺀다.
- 질문마다 앞에 진행 한 줄을 보여 준다. 예: "다룸: 왜 ✓ · 누구 ✓ · 기술 선택(지금) · 디자인(남음)".
- 주제가 8개를 넘게 커지면 스펙을 여러 개로 나눌지 묻는다(sorbh판).

### 5-4. 조사가 필요한 선택
- **찾는 순서:**
  1. 조사 창고. 위치는 아직 없다(10장). `references/research.md`에 자리만 두고, 없으면 건너뛴다.
  2. 디자인 질문이면 디자인 씨앗 저장소(design-brain 스킬이 입구).
  3. 웹: 공식 문서(Claude 문서 등), Hugging Face, GitHub 저장소, 그 도구의 공식 문서.
- **후보를 보여 주는 모양:** 후보마다 무엇인지, 이 프로젝트에 맞는 이유와 안 맞는 이유, 비용, 출처 링크와 확인한 날짜. 추측 답(추천)은 이유와 함께 붙일 수 있지만, 고르는 건 도하다. 후보가 5개 이상이면 목록은 글로(디자인 레퍼런스가 많으면 페이지로) 보여 주고, 팝업에는 추천 3개와 기타 칸만 둔다(4장 14번).
- **디자인 레퍼런스:** 넓게 보여 주고 도하가 고른다. `playbooks/idea-candidates.md`의 방식을 따른다(무거운 후보는 말로 설명, 고르지 않은 후보도 남김).
- **조사 기록:** 조사 결과는 새 프로젝트의 조사 기록 문서에 출처와 날짜를 붙여 남긴다. 다음 세션이 같은 조사를 다시 하지 않게 하기 위해서다. 늘 같은 모양(후보, 고른 것, 출처, 확인한 날짜)으로 써서, 나중에 조사 창고가 모아 가기 쉽게 한다(4장 15번).
- 유료 도구는 쓰기 전에 묻는다. 웹 조사를 서브에이전트에 나눠 맡길 때는 출처 링크와 핵심 사실만 받고, 도하에게 보여 주기 전에 중요한 출처는 메인 세션이 직접 연다(`skills/lean-context/FEEDBACK.md` 2026-11-20: 긴 파일을 서브에이전트에 맡기면 세부가 빠질 위험).

### 5-5. 되짚기
- 6줄로 되짚는다: 결과 / 누구를 위해 / 왜 지금 / 성공의 모습 / 가장 강한 제약 / 안 할 것. 도하의 말을 되도록 그대로 쓴다. "안 할 것"은 빼지 않는다(addyosmani판 4단계).
- 도하가 분명히 "맞다"고 해야 넘어간다. "알아서 해", "좋아요", "그냥 시작하자"는 "맞다"가 아니다. 구체적인 두 선택지로 다시 묻거나 "고칠 곳 있나요?"라고 묻는다(addyosmani판 5단계).
- 스스로 시험한다: "다음에 물을 질문 세 개에 도하가 뭐라고 답할지 맞힐 수 있나?" 못 맞히면 아직 끝이 아니다.
- 여러 번 물어도 확신이 오르지 않으면 멈추고 말한다: "질문을 N개 했는데도 답을 짐작하지 못하겠어요. 기초가 빠진 것 같은데, 한 발 물러서서 볼까요?"
- **(2판)** 다룰 주제가 다 채워진 뒤 되짚는다. 6줄을 "도하가 답한 것 / AI가 짐작하거나 기본값으로 둔 것" 두 묶음으로 보여 준다(4장 22번). "맞다" 뒤에는 확정된 6줄과 다음 단계 제안만 쓰고 그 답에서 멈춘다. 질문 팝업도 부르지 않는다(4장 20·24번).

### 5-6. 그림 미리보기와 고치기 (2판, 소프트웨어)
- 되짚기에 "맞다" → 멈춤 → 도하가 미리보기를 고르면, AI가 이해한 구조·데이터 흐름·사용자 흐름·화면·만드는 순서를 그림 위주 페이지(아티팩트)로 보여 준다. 도하가 고칠 곳을 말하면 같은 주소에 고쳐 올리고, 분명히 승인할 때까지 되풀이한다(sorbh판 4단계, 4장 21·23번).
- 그림은 mermaid 기본. 화면처럼 손으로 고치는 게 나은 것은 도하가 원하면 Figma로 그린다(4장 21·32번). 승인한 그림의 원본은 설계 문서에 넣는다(4장 28번).
- 창작물이면 건너뛴다(4장 34번). 자세한 것은 `references/preview.md`.

### 5-7. 끝 검사
- 앞 대화를 모르는 새 맥락 서브에이전트에게 스펙 초안만 주고 두 가지를 시킨다.
  1. 빌더 점검: `skills/plan-first/references/builder-check.md`의 프롬프트.
  2. 공격 읽기: 이 프로젝트에 해당하는 것만(실패하는 경우, 커질 때 무너지는 곳, 보안 빈틈, 서로 부딪히는 결정, 운영, 데이터가 꼬이는 곳, 남의 도구에 기대는 위험). 이미 인터뷰에서 답한 것은 다시 올리지 않게 결정 표를 함께 준다(sorbh판 3단계).
- 돌아온 것을 세 무더기로 나눈다(plan-first 3장과 같음): 이미 답이 있음 → 문서에 씀 / 사소함 → AI가 정하고 "내 판단"으로 표시 / 도하만 답할 수 있음 → 하나씩 묻는다.
- 도하만 답할 수 있는 질문이 0개가 되면 인터뷰를 끝낸다.
- **(2판)** 돌아온 것은 먼저 번호 목록으로 요약하고, 작은 것은 큰 것과 중간 것을 다 푼 뒤 한 질문으로 묶어 넘긴다(보안은 묶지 않음). 끝나면 "도하가 답한 것 / AI가 정하거나 짐작한 것" 두 묶음으로 요약한다(sorbh판 3단계, 4장 21·22번).

### 5-8. 문서로 넘기기
- 새 프로젝트 폴더에 프로젝트 크기에 맞게 쓴다(크기 표는 `playbooks/new-project-kickoff.md` 2장).
  - **원문 기록:** 도하의 첫 요청과 인터뷰 답을 고치지 않고(틀: `templates/USER_DIRECTIONS.md`).
  - **스펙 = 설계 문서:** 틀은 `skills/plan-first/references/design-doc.md`. 1장에 5-5의 확정된 6줄을 둔다. 결정 표에는 누가 정했는지와 근거, 날짜를 쓴다.
  - **조사 기록:** 후보, 고른 것, 출처, 날짜.
  - **CLAUDE.md:** `templates/CLAUDE.md`를 바탕으로 쓴 뒤, `references/six-shifts.md`의 점검 질문 6개로 점검한다. 무엇을 빼고 바꿨는지 도하에게 보고한다.
  - **세션 계획:** 틀은 `skills/plan-first/references/session-plan.md`.
  - **상태 문서:** HANDOFF.md 또는 STATUS.md에 다음 세션 시작 프롬프트 하나만 쓴다(`skills/session-handoff/SKILL.md` 3~4장).
- 그다음 멈춘다. 다음 세션은 도하가 시작하거나, AI가 새 세션 카드를 제안한다. 인터뷰한 세션은 만들기를 시작하지 않는다(addyosmani판 6단계와 같은 뜻).
- 인터뷰가 길어져 세션이 무거워지면 지금까지를 문서에 저장하고 새 세션에서 이어 간다(`skills/session-handoff/SKILL.md` 2장). 저장한 문서에 "다룬 주제 / 남은 주제"를 두어 이어 하기 쉽게 한다(sorbh판의 이어 하기). **(2판)** 이어 하기는 상태 파일(`.reverse-prompt.json`)로 한다(4장 30번).
- **(2판)** 설계 문서에 결정 표(7칸)와 "의존 관계와 만드는 순서" 장을 꼭 두고, 소프트웨어면 구조 장도 꼭 둔다. 승인한 그림의 mermaid 원본과 Figma 주소를 구조 장, 화면 장에 넣는다. 세션 계획은 만드는 순서 장을 따라 나누고, 화면을 만드는 세션에 Figma 왕복과 도하가 고른 화면 디자인 스킬을, 큰 덩어리를 마치는 세션마다 어긋남 검사를 넣는다(4장 21·22·25·27~31번).

### 5-9. 만든 뒤 스펙과 코드 어긋남 검사 (2판, 소프트웨어)
- `/reverse-prompt --verify <설계 문서>`나 "만든 게 설계대로인지 봐 줘"로 부른다. 인터뷰가 아니라 검사다. 보고 전에는 아무것도 쓰지 않고, 코드는 고치지 않는다. 설계 문서를 본 AI와 보지 않은 AI 둘이 따로 보고 맞댄다. 지적마다 도하가 정한다(sorbh판 VERIFY.md, 4장 21·33번). 자세한 것은 `references/verify.md`.
