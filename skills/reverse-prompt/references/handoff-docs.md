# 넘길 문서

> reverse-prompt 8장에서 엽니다. 끝 검사가 끝난 뒤 씁니다. 틀은 새로 만들지 않고 아래 틀을 가리킵니다. 상태 파일(이 파일 4장)은 인터뷰 중에도 씁니다. 2판(2026-11-24)에서 꼭 둘 장, 세션 계획에 넣을 것, 상태 파일을 더함.

**목표:** 앞 대화를 모르는 새 세션이 이 문서만 읽고, 도하에게 다시 묻지 않은 채 만들기를 시작할 수 있다.

## 1. 무엇을 쓰나 (크기에 맞게)

크기 표는 `~/MY_PROJECT/second_brain/playbooks/new-project-kickoff.md` 2장에 있습니다. 작은 프로젝트면 아래 몇 개를 합쳐도 됩니다(예: 조사 기록을 설계 문서의 한 장으로). 상태 파일은 크기와 상관없이 씁니다.

| 문서 | 담는 것 | 틀 |
|---|---|---|
| 원문 기록(`USER_DIRECTIONS.md`) | 도하의 첫 요청과 인터뷰 답(팝업 답 포함)을 고치지 않고 날짜와 함께 | `~/MY_PROJECT/second_brain/templates/USER_DIRECTIONS.md` |
| 스펙 = 설계 문서(`DESIGN.md`) | 1장에 되짚기에서 확정된 6줄(두 묶음 그대로). 2장의 꼭 둘 장. 반박 뒤에도 생각이 달랐으면 두 쪽 다 | `~/.claude/skills/plan-first/references/design-doc.md` + 2장 |
| 조사 기록(`RESEARCH.md`) | 후보, 고른 것, 출처, 확인한 날짜 | `research.md` 4장의 모양 |
| `CLAUDE.md` | 그 프로젝트의 규칙 파일. 5장대로 점검 | `~/MY_PROJECT/second_brain/templates/CLAUDE.md` |
| 세션 계획 | 세션마다 전제, 목표, 읽을 것, 할 일, 멈출 곳, 완성 기준. 3장의 넣을 것 | `~/.claude/skills/plan-first/references/session-plan.md` |
| 상태 문서(`HANDOFF.md` 또는 `STATUS.md`) | 다음 세션 시작 프롬프트 하나만 | `~/.claude/skills/session-handoff/SKILL.md` 3~4장 |
| 상태 파일(`.reverse-prompt.json`, `.reverse-prompt.cache.json`) | 이어 하기와 어긋남 검사에 쓰는 기계용 기록 | 4장 |

- "알아서 해", "좋아요"를 도하의 결정으로 적지 않습니다. 그런 답 뒤에 AI가 정한 것은 "내 판단"입니다.
- 한 사실은 한 곳에만 씁니다. 결정은 설계 문서, 원문은 원문 기록, 진행은 상태 문서와 상태 파일에 두고, 다른 문서는 "파일 + 장"으로 가리킵니다.

## 2. 설계 문서에 꼭 둘 장

설계 문서 틀의 장에 더해 아래 장을 둡니다. 장 이름은 그대로 씁니다. 어긋남 검사(`verify.md`)가 이 이름으로 장을 찾습니다.

- **결정 표**(늘): 칸은 늘 이 일곱 개입니다. 값이 비어도 칸을 빼지 않습니다.

  ```markdown
  | ID | 주제 | 결정 | 누가 | 근거 | 출처 | 날짜 |
  |---|---|---|---|---|---|---|
  | D1 | 저장소 | Supabase | 도하 | 조사 기록 1장, 도하의 말 "무료 범위면 충분" | 인터뷰 | 2026-11-24 |
  ```
  - ID: D1, D2… 한번 붙이면 바꾸지 않습니다. 뒤의 줄이 이 번호로 앞 줄을 가리킵니다.
  - 누가: 도하 / 내 판단. 출처: 인터뷰 / 미리보기 / 끝 검사 / 어긋남 받아들임. 날짜: YYYY-MM-DD.
  - 표에 줄을 더할 때는 "결정 표" 장의 표 끝을 찾아 그 안에 넣습니다. 결정 표가 문서의 마지막 장이라고 짐작하지 않습니다.
- **의존 관계와 만드는 순서**(늘): 덩어리 사이의 의존(무엇이 무엇에 기대나)과 만드는 순서. 소프트웨어면 미리보기에서 승인한 의존 그림의 mermaid 원본을 넣고, 그 아래에 층마다 무엇을, 왜 그 순서로 만드는지를 목록으로 씁니다. 창작물이면 만드는 순서만 글로 씁니다. 세션 계획은 이 장을 따라 나눕니다(3장).
- **구조**(소프트웨어면 늘): 어디서 돌아가나, 큰 덩어리와 그 사이 연결, 바깥 도구, 데이터가 어디서 들어와 어디에 쌓이나. 미리보기에서 승인한 구조 그림과 데이터 흐름 그림의 mermaid 원본을 넣습니다. **그림은 미리보기 페이지가 아니라 이 장에 둡니다.** 다음 세션은 페이지가 아니라 설계 문서를 읽고, 어긋남 검사도 이 장의 문장을 기준으로 봅니다.
- **화면과 흐름**(화면이 있으면): 화면 목록, 사용자 흐름 그림(mermaid 원본), 화면마다 무엇이 어디에 놓이나. Figma로 그렸으면 Figma 주소와, 도하가 고친 뒤의 모습을 한두 줄로. 화면을 만들 때 쓸 화면 디자인 스킬(인터뷰에서 도하가 고른 것)과 고른 디자인 레퍼런스(조사 기록의 어느 장).
- 그 밖에 인터뷰 주제에 따라 장을 더합니다(데이터, 실패 처리, 운영 같은 것). 보안 문제가 나왔으면 보안 장은 꼭 둡니다.
- 미리보기를 올렸으면 설계 문서 머리에 그 주소를 한 줄 적습니다.

## 3. 세션 계획에 넣을 것

- **세션은 "의존 관계와 만드는 순서" 장을 따라 나눕니다.** 따로 할 일 목록을 만들지 않습니다. 세션 계획이 세션마다 할 일을 담고 있어서, 목록을 따로 두면 비슷한 목록이 두 곳에 생깁니다(도하, 2026-11-24).
- **화면이 있는 소프트웨어면** 화면을 만드는 세션의 할 일에 둘을 적습니다.
  - Figma 왕복: AI가 Figma에 화면 배치 초안을 만듦 → 도하가 위치를 옮기고 고침 → AI가 도하가 고친 것을 읽고(`get_design_context`, `get_screenshot`) 그 방향으로 다듬음. 도하가 해 보니 잘 통했다고 한 방식입니다. Figma 도구를 쓰기 전에 Figma 스킬(`figma:figma-use`)을 먼저 엽니다. 이 단계는 도하가 손을 대야 하니 멈출 곳으로 적습니다.
  - 쓸 화면 디자인 스킬: 설계 문서 "화면과 흐름" 장에 적은 것.
- **소프트웨어면** 만드는 순서의 큰 덩어리(층)를 마치는 세션마다, 완성 기준에 "어긋남 검사(`/reverse-prompt --verify <설계 문서>`)에서 큰 지적과 중간 지적이 0개, 또는 도하가 하나씩 정함"을 넣습니다.

## 4. 상태 파일

새 프로젝트 폴더에 두 파일을 둡니다. 도하가 읽는 파일이 아니라 AI가 이어 하기와 어긋남 검사에 쓰는 기계용 기록입니다. 질문과 답은 원문 기록에 이미 있으니 어느 쪽에도 다시 담지 않습니다.

**`.reverse-prompt.json`(git에 올림)**

```json
{
  "specPath": "DESIGN.md",
  "projectKind": "software",
  "stage": "interview",
  "updatedAt": "YYYY-MM-DD",
  "coverage": { "왜": "done", "기술 선택": "in-progress", "디자인": "pending" },
  "preview": { "status": "none", "url": null, "figmaUrl": null },
  "finalCheck": { "status": "pending", "findings": [] },
  "capturedAtCommit": null,
  "reconciledAt": null,
  "baseline": { "derivedFrom": null, "claims": [] },
  "driftLedger": []
}
```

| 칸 | 뜻 |
|---|---|
| `projectKind` | `software` / `creative` / `mixed` |
| `stage` | `interview` / `restate`(되짚기) / `preview` / `final-check` / `handed-off`(넘김) |
| `coverage` | 다룰 주제마다 `pending`(남음) / `in-progress`(지금) / `done`(다룸) |
| `preview.status` | `none` / `shown`(올림) / `approved`(승인) / `skipped`(건너뜀) |
| `finalCheck.findings` | 끝 검사에서 찾은 것: `{ "id": "F1", "title": "...", "severity": "큼", "dimension": "보안 빈틈", "status": "open" }`. `status`는 `open` / `answered` / `decided`(내 판단) / `acknowledged`(알고 넘김) |
| `capturedAtCommit` | 기준 커밋: 설계 문서가 마지막으로 코드와 맞춰진 커밋. 인터뷰 때는 코드가 없으니 `null` |
| `reconciledAt` | 어긋남 검사 뒤 설계 문서를 코드에 맞춰 고친 날 |
| `baseline.claims` | 검사할 문장 목록: 설계 문서에서 그대로 옮긴, 코드로 확인할 수 있는 문장들(`verify.md` 2단계) |
| `driftLedger` | 받아들인 어긋남: 도하가 "코드 쪽이 맞다"고 정한 것. 다음 검사에서 다시 올리지 않으려고 적어 둠(`verify.md` 11단계) |

**`.reverse-prompt.cache.json`(git에서 뺌)**: 어긋남 검사가 코드를 훑어 만든 목록, 문장마다 찾은 근거와 판정, 마지막으로 검사한 커밋(`lastVerifiedCommit`). 지워도 다음 검사가 다시 만듭니다. `.gitignore`에 이 파일 이름을 넣습니다.

- **쓰는 때:** 미리보기를 올릴 때, 끝 검사 결과를 받을 때, 세션을 넘길 때, 문서로 넘길 때. 처음 쓰는 때는 그중 먼저 오는 때입니다. 쓸 때마다 `stage`와 `updatedAt`을 고칩니다.
- **읽는 때:** 이 스킬을 다시 불렀는데 폴더에 상태 파일이 있을 때(SKILL.md 0장의 이어 하기), 어긋남 검사를 할 때.
- 모르는 칸이나 빠진 칸이 있어도 멈추지 않습니다. 빈 값으로 보고 계속합니다.

## 5. 6가지 지침으로 점검하기

6가지 지침(`six-shifts.md`)은 더 똑똑한 모델에게는 규칙과 예시를 덜 주고 판단에 맡기라는 Claude 쪽 안내입니다. 도하는 이 지침을 **새 프로젝트가 만드는 지침 문서에만** 적용하기로 했습니다. 새 프로젝트의 `CLAUDE.md`를 쓴 뒤 6개 질문으로 점검하고, 스펙과 그 프로젝트가 만드는 스킬에도 해당하는 것만 봅니다. 이 스킬 자체나 second_brain 전체에는 적용하지 않습니다.

| # | 지침 | 새 프로젝트에서 볼 곳 |
|---|---|---|
| 1 | 규칙 → 판단 | "반드시 ~한다"를 이유가 붙은 원칙으로 바꿀 수 있나. 같은 행동을 낳는다면 원칙이 낫다 |
| 2 | 예시 → 인터페이스 설계 | 예시를 늘어놓는 대신, 만들 스크립트와 도구의 입력(매개변수, 파일 모양)을 알아보기 쉽게 정했나 |
| 3 | 다 앞에 → 필요할 때 열기 | CLAUDE.md에 늘 필요하지는 않은 절차가 있나. 있으면 설계 문서의 장이나 스킬로 빼고 가리킨다 |
| 4 | 되풀이 → 한 곳 | 공통 규칙(`~/.claude/CLAUDE.md`)이나 스킬에 이미 있는 말(한국어로 답하기, 질문 팝업, 쉬운 말)을 CLAUDE.md에 또 쓰지 않았나 |
| 5 | CLAUDE.md의 기억 → 자동 메모리 | 도하의 취향과 피드백 같은 기억을 손으로 적지 않았나. 그건 자동 메모리가 맡는다. 진행 상태(HANDOFF, STATUS)는 기억이 아니라 기록이라 남긴다 |
| 6 | 단순한 스펙 → 풍부한 참고 | 글로만 설명하는 대신 보여 줄 것이 있나: 승인한 그림, 고른 디자인 레퍼런스의 링크나 페이지, 시험(테스트) 묶음, 따라 할 남의 코드 |

- 점검한 뒤 무엇을 빼고 바꿨는지 도하에게 한 줄씩 보고합니다. 틀(`templates/CLAUDE.md`)에서 뺀 장도 적습니다.

## 6. 끝내기

- 다 쓴 뒤 문서끼리 어긋난 곳이 없는지 한 번 봅니다(같은 결정이 두 곳에 다르게 적히지 않았나, 설계 문서의 그림과 미리보기의 마지막 판이 같나).
- 상태 파일의 `stage`를 `handed-off`로 적습니다.
- 도하에게 알립니다: 만든 문서 목록, 다음 세션 시작 프롬프트, 도하가 확인할 것 하나.
- 그다음 멈춥니다. 만들기는 다음 세션의 일입니다. 새 세션 카드를 제안할 수 있으면 제안하고, 시작은 도하가 합니다.
