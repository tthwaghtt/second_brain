# 다룰 주제 목록

> reverse-prompt 3장에서 엽니다. 대본이 아닙니다. 프로젝트에 맞게 늘이고 빼고, 큰 주제는 쪼갭니다(예: 기술 선택 → 화면, 서버, 저장소).

**주제가 "다 됐다"의 기준:** 스펙을 받은 세션이 그 주제에 대해 도하에게 다시 묻지 않고 만들 수 있다. 도하가 "아직 모른다"고 해도 답입니다. 스펙의 "아직 모르는 것"에 언제 알게 되는지와 함께 적으면 그 주제는 다 된 것입니다.

## 1. 늘 다룸 (의도)

| 주제 | 알아낼 것 |
|---|---|
| 왜 | 왜 만드는지, 왜 지금인지. 가장 먼저 묻는다 |
| 누구 | 누가 쓰나(도하 혼자, 팀, 바깥 사람). 그 사람은 지금 어떻게 하고 있나 |
| 성공의 모습 | 무엇이 되면 성공인가. 잴 수 있게(예: 릴스 하나를 10분 안에 올릴 수 있다) |
| 안 할 것 | 이번에 만들지 않는 것. 실패의 모습(돌아가도 실패인 것) |
| 가장 강한 제약 | 돈, 시간, 기술, 법 가운데 무엇이 가장 세게 묶나 |
| 이미 있는 것 | 비슷한 도구를 써 봤나, 이미 쓰는 계정·데이터·코드가 있나 |
| 도하의 문장 | 요청에서 두 가지로 읽히는 낱말과 문장(원문 읽기 표의 "모호한 곳") |

## 2. 새 프로젝트면 더함 (만드는 방법)

조사 칸이 "필요"인 주제는 후보 없이 묻지 않습니다(`research.md`).

| 주제 | 알아낼 것 | 조사 |
|---|---|---|
| 기술 선택 | 언어, 프레임워크, 쓸 AI 모델과 바깥 도구 | 필요 |
| 구조 | 어디서 돌아가나(내 맥, 웹, 휴대폰, 클라우드), 큰 덩어리와 그 사이의 연결. 소프트웨어면 설계 문서에 구조 장으로 꼭 남는다(`handoff-docs.md` 2장) | 때때로 |
| 데이터 | 무엇을 저장하나, 어디에, 얼마나 오래, 언제 지우나 | 때때로 |
| 배포와 운영 | 어디에 올리나, 누가 켜고 끄나, 고장 나면 어떻게 아나 | 때때로 |
| 디자인 | 그 프로젝트에 맞는 갈래: UI, 모션, 사진, 영상, 소리, 글꼴과 색, 브랜드, 글의 말투 등. 레퍼런스가 있나 | 필요(design-brain 먼저) |
| 비용 | 한 달에 쓸 수 있는 돈, 유료 API와 구독 | 가격은 조사 |
| 비밀값과 개인정보 | 어떤 키가 필요한가, 남의 개인정보를 다루나 | — |
| 법과 라이선스 | 플랫폼 약관(예: 인스타 자동화), 남의 코드·글꼴·음악의 라이선스 | 필요 |
| 세션 크기 | 몇 세션쯤 되나, 한 세션에 어디까지 | — |
| 승인 지점 | 무엇은 묻고 무엇은 바로 해도 되나 | — |
| 건드리면 안 되는 것 | 파일, 폴더, 계정 | — |
| 프로젝트 폴더 | 문서를 쓸 위치(없으면 묻는다) | — |
| 완성 기준 | 잴 수 있는 기준과 확인하는 방법 | — |

## 3. 프로젝트 종류에 따라 더함 (예)

- **화면이 있는 소프트웨어(웹, 앱):** 화면과 사용자 흐름(어떤 화면이 있나, 사용자가 화면 사이를 어떻게 옮겨 가나, 화면마다 무엇이 놓이나). 그림 미리보기(SKILL.md 6장)에 화면을 그리려면 여기서 물어야 합니다. 화면을 만들 때 쓸 화면 디자인 스킬(이 컴퓨터에 있는 impeccable, design-taste-frontend, Figma 스킬 같은 것)은 `research.md`대로 후보와 하는 일을 보여 주고 도하가 고릅니다. 고른 것은 설계 문서의 "화면과 흐름" 장과 세션 계획에 적습니다.
- **콘텐츠 자동화(릴스, 쇼츠, 카드 뉴스):** 원본(영상, 글)은 어디서 오나, 사람이 고르는 지점은 어디인가, 올리기까지 자동인가, 플랫폼 약관과 API 제한.
- **여러 사람이 같이 쓰는 앱:** 로그인과 권한, 둘이 동시에 고치면 누구 것이 남나, 인터넷이 끊겼을 때.
- **AI 기능이 들어감:** 어떤 모델, 한 번 부를 때 드는 돈, AI가 틀린 답을 내면 사람이 어디서 보나.
- **데이터 분석·수집:** 데이터 출처와 약관, 얼마나 자주 모으나, 결과를 누가 어떻게 보나.
- **바깥 독자가 보는 결과물(페이지, 발표, 전자책):** 독자가 누구인가. 만들 때는 reader-check 스킬(결과물 독자 검사)을 쓴다고 스펙에 적는다.
- **게임·인터랙션:** 무엇이 재미인가(판단은 도하), 조작 방법, 기기.

## 4. 진행 한 줄과 나누기

- 질문마다 앞에 둡니다: `다룸: 왜 ✓ · 누구 ✓ · 기술 선택(지금) · 디자인(남음)`. 다 된 주제는 ✓, 지금 묻는 주제는 (지금), 아직은 (남음)입니다. 빼기로 한 주제는 적지 않습니다. 한 줄에 들어가게 작은 주제는 묶습니다(예: "의도 ✓").
- 큰 덩어리가 여럿이라(예: 편집기, 자동 올리기, 관리 화면이 각자 기술·데이터·디자인을 따로 가짐) 주제가 8개를 넘게 커지면 스펙을 나눌지 묻습니다. 나누면 무엇을 먼저 만들지와 어느 것이 어느 것에 기대는지를 함께 보여 줍니다.
