# 스펙과 코드 어긋남 검사 (소프트웨어)

> reverse-prompt 9장에서 엽니다. 도하가 `/reverse-prompt --verify <설계 문서>`(전체를 보려면 `--verify --full`)라고 하거나 "만든 게 설계대로인지 봐 줘"라고 할 때 씁니다. sorbh판(sorbh/interview-me)의 `VERIFY.md`를 줄여 한국어로 다시 씀(MIT). GitHub 이슈에 올리는 부분은 뺌.

**이건 인터뷰가 아니라 검사입니다.** 보고가 먼저이고, 질문이 하나도 없어도 됩니다. 도하에게 묻는 질문은 SKILL.md 2장 규칙(질문 팝업, 하나씩)을 따르지만, 보고는 한 번에 다 보여 줍니다.

**쓰기 안전(꼭 지킴):** 0~10단계는 읽기만 합니다. 도하가 11단계에서 할 일을 고르기 전에는 어떤 파일도 쓰거나 고치지 않습니다. 이 검사는 코드를 절대 고치지 않습니다. 쓸 수 있는 파일은 설계 문서와 상태 파일 둘(`.reverse-prompt.json`, `.reverse-prompt.cache.json`)뿐입니다.

**AI 둘을 나누는 까닭:** 4단계와 5단계는 앞 대화를 모르는 서브에이전트 둘이 따로 합니다. 맥락을 아끼려는 게 아니라, 서로의 결과를 못 보게 하려는 것입니다. 설계 문서를 본 AI는 설계 문서의 말에 끌려, 설계에 없는데 코드에 생긴 것을 덜 찾습니다.

## 0. 준비

- 설계 문서 경로를 정합니다. 경로가 없거나 틀리면 프로젝트 폴더와 `docs/`, `specs/`에 있는 설계 문서 후보를 보여 주고 어느 것인지 묻습니다. 혼자 골라잡지 않습니다. 한 번에 설계 문서 하나만 봅니다.
- 고른 파일이 설계 문서가 아니면(코드, 설정, README) 알리고 정말 볼지 확인합니다.
- 창작물 프로젝트(상태 파일의 `projectKind`가 `creative`)면 "이 검사는 소프트웨어용이에요"라고 말하고 멈춥니다.
- git 저장소인지 봅니다(`git rev-parse --is-inside-work-tree`). 아니면 3단계와 6단계가 약해집니다.

## 1. 설계 문서와 상태 읽기

- 설계 문서를 끝까지 읽습니다.
- 상태 파일 둘을 읽습니다. 모양은 `handoff-docs.md` 4장에 있습니다. 상태 파일에 없는 칸이 있으면 빈 값으로 보고 계속합니다.
- 상태 파일이 아예 없어도 됩니다. 빈 상태로 시작하고, 2단계에서 설계 문서의 글로 문장 목록을 만들고, 보고 머리에 "기준 커밋이 없어 전체를 봤다"고 씁니다.

## 2. 검사할 문장 목록

상태 파일에 `baseline.claims`가 있으면 그것을 씁니다. 없으면 설계 문서를 처음부터 끝까지 읽고, 코드로 확인할 수 있는 문장을 뽑습니다.

```json
{ "id": "C1", "type": "component", "area": "구조",
  "quote": "설계 문서의 문장 그대로", "expectedPaths": ["..."], "searchTerms": ["..."] }
```

- `type`: `component`(덩어리), `endpoint`(바깥에서 부르는 입구), `data-model`(데이터 모양), `decision`(결정 표의 줄), `constraint`(제약).
- **`quote`는 설계 문서의 글 그대로 옮깁니다.** 바꿔 쓰지 않습니다. 그대로 옮길 수 없는 문장은 AI가 지어낸 문장입니다.
- **`area`는 지금 붙입니다.** 다룰 주제 이름이나 설계 문서의 장 이름을 씁니다. 그래야 11단계에서 어느 주제가 어긋났는지 바로 압니다.
- **바람이 아니라 확인할 수 있는 것만 뽑습니다.** "쓰기 편해야 한다"는 빼거나 `constraint`로 두고, 판정이 "코드로 확인 못 함"일 것으로 봅니다.
- **결정 표의 줄도 문장입니다**(`decision`). 몰래 뒤집힌 결정을 찾는 길은 이것뿐입니다.
- 만든 목록은 12단계에서 상태 파일에 씁니다(지금은 읽기만).

## 3. 볼 범위 정하기

기본은 바뀐 부분만 봅니다. 아래 가운데 하나라도 맞으면 전체를 보고, 보고 머리에 어느 것 때문인지 씁니다.
- 도하가 `--full`이라고 함
- git 저장소가 아님
- 기준 커밋(`capturedAtCommit`)이 없음, 또는 그 커밋을 찾을 수 없음(`git cat-file -e <커밋>^{commit}` 실패)
- 지난 검사 뒤 설계 문서가 바뀜
- 캐시 파일이 없거나 깨짐

**기준 커밋 고르기:** 상태 파일에 `reconciledAt`(검사 뒤 설계 문서를 코드에 맞춰 고친 날)이 있고, 그 뒤에 설계 문서를 바꾼 커밋이 있으면(`git log -1 --format=%h -- <설계 문서>`), 그 커밋을 이번 검사의 기준으로 쓰고 12단계에서 적습니다.

바뀐 부분만 볼 때는 `git diff --name-only <기준 커밋>..HEAD`와 `git status --porcelain`(커밋하지 않은 것도 바뀐 것)으로 바뀐 파일을 모읍니다.
- 4단계(문장 확인)는 지난 판정이 `implemented`가 아니거나, 그 근거 파일이 바뀐 문장만 다시 봅니다. **지난번에 `not-found`나 `partial`이던 문장은 늘 다시 봅니다.** 아직 안 만든 것은 바뀐 파일 목록에 나타날 수가 없기 때문입니다.
- 5단계(코드 훑기)는 바뀐 파일만 훑어 캐시의 목록에 합칩니다.

## 4. 문장 확인 (첫째 AI)

앞 대화를 모르는 서브에이전트(Explore)에게 문장 목록만 주고 아래 지시문을 보냅니다. 5단계와 한 메시지에 함께 보내 동시에 돌립니다.

```
너는 이 저장소의 코드가 아래 문장들을 만족하는지 확인한다. 문장 목록: <claims>
문장마다 판정 하나만 돌려줘라. 문장을 더하거나, 합치거나, 쪼개거나, 다르게 읽지 마라. 뜻이 흐리면 unverifiable로 하고 이유를 적어라. 네가 고쳐 읽은 문장으로 바꿔 판정하지 마라.
- implemented: 만족함. 파일:줄 근거가 꼭 있어야 한다.
- partial: 일부만 만족함. 파일:줄과 빠진 것을 적어라.
- contradicted: 반대로 정한 흔적을 찾음. 파일:줄.
- not-found: 못 찾음. 실제로 돌린 grep과 glob을 그대로 적어라.
- unverifiable: 본래 코드로 확인할 수 없는 문장(절차, 글, 의도).
테스트, 픽스처, 목업, 예제, 생성된 파일에 있는 근거는 evidenceKind를 "non-production"으로 적어라. 픽스처는 만든 것이 아니다.
검색 목록 없이 not-found를 쓰지 마라. 못 찾았다는 것은 없다는 증거가 아니다.
비밀값(API 키, 토큰, 비밀번호)이 보이면 값은 옮겨 적지 말고 파일:줄만 적어라.
돌려줄 모양: {"verdicts":[{"claimId":"C1","verdict":"...","evidence":["경로:줄"],"evidenceKind":"production","searchesTried":[],"notes":""}]}
```

## 5. 코드 훑기 (둘째 AI, 설계 문서를 보지 않음)

또 다른 서브에이전트(Explore)에게 아래 지시문을 보냅니다. **설계 문서, 문장 목록, 4단계 결과, 설계 문서에 쓰인 낱말을 하나도 주지 않습니다.**

```
이 저장소에 실제로 무엇이 있는지 적어라. 설계 문서나 명세는 열지 마라.
적을 것: 맨 위 짜임과 각 부분의 목적, 모듈과 맡은 일, 바깥에서 부르는 입구와 엔드포인트, 데이터 모양과 스키마, 설정과 빌드 파일, 바깥 의존성. 항목마다 경로와 한 줄 설명.
node_modules, vendor, dist, build는 빼라. 비밀값이 보이면 값은 적지 말고 경로만 적어라.
돌려줄 모양: {"inventory":[{"path":"...","kind":"component|endpoint|data-model|config|dependency","summary":"..."}]}
```

## 6. 자리 옮김 먼저 맞추기 (분류하기 전에)

이걸 먼저 하지 않으면, 파일 하나를 옮긴 것이 "빠짐" 하나와 "설계보다 넘침" 하나로 두 번 보고됩니다. 이런 헛지적이 많은 보고는 한 번 보고 버려집니다.

```
git diff --name-status -M --find-renames=40% <기준 커밋>..HEAD
```

- 판정이 `not-found`나 `partial`인 문장의 `expectedPaths`가 옮겨진 파일의 옛 경로와 맞고, 새 경로가 5단계 목록에서 받쳐 줄 문장이 없으면, 둘을 하나로 합쳐 "자리 옮김"으로 둡니다. git이 낸 비슷함 점수가 근거입니다. 새 경로는 "설계보다 넘침" 후보에서 뺍니다.
- `partial`도 꼭 봅니다. 옮긴 파일은 내용은 맞고 경로만 틀려서 `partial`로 나오기 쉽습니다.
- 40%는 일부러 정한 값입니다. git 기본값 50%를 쓰면, 옮기면서 많이 고친 파일을 옮긴 것으로 못 알아봅니다.
- git이 없거나 기준 커밋을 찾을 수 없으면 파일 이름, 함수 이름, 내용이 비슷한 것끼리 맞춥니다. 확실한 것만 합치고, 보고에 "AI 판단으로 맞춤"이라고 표시합니다.

## 7. 나누고 지문 붙이기

| 이름(보고에 씀) | 기록용 이름(상태 파일에 씀) | 언제 | 기본 심각도 |
|---|---|---|---|
| 빠짐 | `missing` | `not-found`이고 자리 옮김으로 설명되지 않음 | 중간 |
| 자리 옮김 | `relocated` | `not-found`나 `partial`이 6단계의 자리 옮김과 맞음 | 작음 |
| 덜 됨 | `incomplete` | `partial`이고 자리 옮김으로 설명되지 않음 | 중간 |
| 설계보다 넘침 | `exceeded` | 5단계 목록에 있는데 받쳐 주는 문장이 없음(아래 뺄 것은 빼고) | 작음 |
| 반대로 됨 | `contradicted` | 반대로 정한 흔적이 있음 | 중간 |
| 코드로 확인 못 함 | `unverifiable` | 본래 코드로 볼 수 없는 문장 | 작음 |

- **판정마다 갈 곳이 하나씩 있습니다.** `implemented` → 지적 없음, `not-found` → 자리 옮김 또는 빠짐, `partial` → 자리 옮김 또는 덜 됨, `contradicted` → 반대로 됨, `unverifiable` → 코드로 확인 못 함. 이 표에 없는 판정이 나오면 버리지 말고 "덜 됨, 사람이 봐야 함"으로 보고하고, 이 안내가 예상하지 못한 판정이라고 씁니다. 판정을 말없이 버리면 "지적 0개"라는 거짓 보고가 됩니다.
- **심각도 고치기:** 로그인과 권한, 데이터 다루기, 설계 문서에 적은 제약에 걸린 빠짐과 반대로 됨은 올리고, 도우미 기능의 빠짐은 내립니다. 보안 갈래는 8단계에서 "큼"으로 올립니다. 심각도는 끝 검사와 같은 큼·중간·작음만 씁니다.
- **"설계보다 넘침" 후보에서 뺄 것**(보고하지 않음): 검사하는 설계 문서 자신, 다른 설계 문서와 상태 파일 둘, 편집기와 AI 설정 폴더(`.claude/`, `.vscode/`, `.idea/` 등. 정말 위험한 것이 있으면 8단계 보안으로), 설계 문서가 쓰라고 한 바깥 도구(설계 문서가 `git`을 쓰라고 했으면 git은 넘침이 아님). 넘침은 설계보다 자라난 제품만 뜻합니다.
- **지문:** `문장 번호:기록용 이름:근거 경로`(예: `C1:relocated:src/new/path.ts`. 경로는 저장소 기준, 줄 번호는 뺌). 넘침은 문장 번호 자리에 `-`를 씁니다. 받아들인 어긋남은 지적 번호가 아니라 이 지문으로 알아봅니다. 번호는 지적 하나가 끼어들면 밀리지만 지문은 그대로입니다.
- **반대로 됨은 늘 "사람이 봐야 함"입니다.** 어떤 검색도 의도가 뒤집혔다는 것을 증명하지 못합니다. 저절로 받아들임에 적지 않고, 11단계에서 늘 도하에게 묻습니다.
- **근거 규칙(예외 없음):** 지적마다 파일:줄 근거가 있어야 합니다. 빠짐이면 실제로 돌린 검색 목록이 있어야 합니다. 없으면 보고하기 전에 버립니다.

## 8. 보안 (막기)

보안 갈래 여섯: 개인정보를 암호화나 접근 제한 없이 다룸 / 로그인이나 권한을 건너뛸 수 있음 / 입력을 그대로 실행함(SQL, XSS, 명령) / 비밀값이 평문으로 있음 / 공개 입구에 요청 횟수 제한이 없음 / 데이터를 지우는 방법 없이 쌓음.

여기에 맞는 지적은:
1. 심각도를 "큼"으로 올립니다.
2. 묶어 넘길 수 없습니다.
3. 다 풀거나 도하가 위험을 받아들인다고 할 때까지 11단계의 쓰기를 모두 막습니다.
4. 받아들이려면 도하가 이유를 글로 써야 합니다. 그 이유는 상태 파일과 결정 표 둘 다에 남깁니다.

보고는 언제나 끝까지 보여 줍니다. 읽기는 늘 안전하고, 보안 지적 하나에 검사를 멈추면 헛지적 하나로 검사 전체가 막힙니다. 비밀값은 보고에도 옮겨 적지 않고 파일:줄만 씁니다.

## 9. 이미 받아들인 어긋남 빼기

- 지문이 상태 파일의 `driftLedger`에 있으면 목록에서 빼고, 보고 머리에 뺀 개수만 씁니다.
- 지문이 바뀌었으면 어긋남이 움직인 것이니 새 지적으로 다시 올립니다. 잘못이 아니라 바라는 동작입니다.
- `acknowledged`(알고 넘김)로 적힌 것도 빼되, 머리에 "남은 것"으로 심각도와 함께 셉니다.


- 머리에는 늘 씁니다: 설계 문서, 기준 커밋 → 지금, 문장 수, 지적 수, 바뀐 부분만 봤는지 전체를 봤는지(전체면 그 까닭). 자리 옮김을 AI 판단으로 맞췄으면 그것도 씁니다.
- **아직 거의 안 만든 설계:** 근거가 하나라도 나온 문장이 20%보다 적으면, 지적을 늘어놓지 않고 이렇게만 말하고 멈춥니다: "<설계 문서>는 아직 거의 만들어지지 않은 것 같아요(문장 14개 중 1개만 찾음). 다른 곳에서 만들고 있다면 `--full`로 다시 하거나 맞는 설계 문서를 알려 주세요." 할 일 제안도 하지 않습니다. 시작도 안 한 설계에 지적 수십 개를 늘어놓는 것은 쓸모가 없습니다.
- **지적 0개:** 깨끗하게 보고합니다. 확인한 문장, 본 범위, 건너뛴 문장을 씁니다. 설계 문서와 코드가 맞습니다.
- 도하가 원하면 같은 보고를 페이지(아티팩트)로도 올립니다. 묻고 나서 올립니다.

## 11. 할 일 고르기 (여기서부터 쓸 수 있음)

보안 지적이 풀리지 않고 남아 있으면 이 단계 전체가 막힙니다.

지적마다 심각도 순으로 하나씩 질문 팝업으로 묻습니다. 인터뷰처럼 짚을 것은 짚습니다.

| 고를 것 | 하는 일 |
|---|---|
| 코드를 고침 | 아무것도 쓰지 않습니다. 코드는 다음 만들기 세션이 고친다고, 이 지적은 다음 검사에 다시 나온다고 말합니다 |
| 어긋남 받아들임 | 코드 쪽이 맞습니다. 상태 파일의 `driftLedger`에 적고, 결정 표에 출처 "어긋남 받아들임" 줄을 더합니다 |
| 이 주제 다시 묻기 | 설계와 코드 가운데 무엇이 맞는지 다시 정할 만합니다. 그 주제만 다시 인터뷰합니다(아래) |
| 알고 넘김 | 상태 파일에 `acknowledged`로 심각도와 함께 적습니다. 다음 검사에서 빼되 머리에 남은 것으로 셉니다 |

- 보안 지적에는 "알고 넘김"이 없고, "위험 받아들임"은 도하가 쓴 이유가 있어야 합니다.
- 큰 것과 중간 것을 다 푼 뒤, 남은 작은 것을 한 번에 "알고 넘김"으로 할지 묻습니다. 보안 지적은 이 묶음에 넣지 않습니다.
- **받아들인 어긋남은 두 곳에 다 남깁니다.** `driftLedger`는 다음 검사를 조용하게 하는 기계용 걸러내기이고, 결정 표의 줄은 사람이 나중에 읽는 기록입니다. 한 곳에만 있으면 받아들인 것이 안 보이거나, 다음 검사에 또 나옵니다.

  ```json
  "driftLedger": [{ "fp": "C1:relocated:src/new/path.ts", "status": "accepted",
                    "acceptedAt": "YYYY-MM-DD", "rationale": null, "decisionId": "D11" }]
  ```
  `status`: `accepted`(받아들임) / `risk-accepted`(보안 위험 받아들임, `rationale` 꼭 있음) / `acknowledged`(알고 넘김).
- **이 주제 다시 묻기:**
  1. 그 주제만 상태 파일의 `coverage`에서 `pending`으로 돌립니다. 다른 주제는 건드리지 않습니다.
  2. 그 주제만 SKILL.md 2장 규칙(하나씩, 추측 답)으로 다시 묻습니다.
  3. 어긋난 문장이 있는 설계 문서의 장을 **그 자리에서** 고칩니다. 결정 표에 줄을 더하기만 하면 틀린 문장이 그대로 남습니다.
  4. 결정 표에 줄을 더합니다. 결정 표가 설계 문서의 마지막 장이라고 짐작하지 않습니다. "결정 표" 장의 표 끝을 찾아 그 안에 넣습니다.
  5. 주제를 `done`으로 돌립니다.

  **고칠 내용은 diff로 보여 주고 도하가 확인한 뒤에 저장합니다.** 도하나 다른 세션이 쓴 글을 고치는 일이기 때문입니다. 어긋나지 않은 장은 건드리지 않습니다.

## 12. 상태 저장

11단계 말고 쓰는 곳은 여기뿐입니다.

- `.reverse-prompt.json`: 2단계에서 만든 문장 목록(`baseline.claims`, `baseline.derivedFrom: "spec-prose"`), 11단계의 `driftLedger`와 `coverage` 변화, 3단계에서 고른 기준 커밋.
- `.reverse-prompt.cache.json`: 5단계 목록(합친 것), 문장마다 근거 경로와 판정, `lastVerifiedCommit`(지금 HEAD). git 저장소가 아니면 캐시는 쓰지 않습니다.
- **기준 커밋(`capturedAtCommit`)은 설계 문서를 코드와 맞춘 커밋을 가리킵니다.** AI는 커밋하지 않습니다(공통 규칙: 커밋은 도하가 말할 때만). 11단계에서 설계 문서를 고쳤으면 기준 커밋은 그대로 두고, `reconciledAt`에 오늘 날짜를 적고, 도하에게 "설계 문서를 커밋해 주시면 다음 검사 때 그 커밋을 기준으로 적을게요"라고 말합니다. 그래서 상태 파일은 설계 문서를 고친 커밋의 다음 커밋에 들어갑니다.
- 설계 문서를 고치지 않은 검사(읽기만 함)는 기준 커밋을 옮기지 않습니다. 코드를 본 것만으로는 설계 문서가 코드를 따라잡은 것이 아닙니다.
- 커밋을 고쳐 쓰면(amend, rebase, squash) 기준 커밋을 찾을 수 없게 되어 그 뒤 검사는 늘 전체를 봅니다. 도하에게 그렇게 말해 둡니다. 낡았지만 찾을 수 있는 기준은 전체 검사 한 번의 비용이지만, 찾을 수 없는 기준은 매번 전체 검사의 비용입니다.

## 지킬 것

1. 0~10단계는 아무것도 쓰지 않는다.
2. 근거(파일:줄, 빠짐이면 검색 목록) 없는 지적은 보고에 남지 않는다.
3. 코드 훑기 AI(5단계)는 설계 문서를 보지 않는다.
4. 자리 옮김은 분류하기 전에 맞추고, `not-found`와 `partial`을 다 본다.
5. 판정마다 갈 곳이 하나씩 있다. 말없이 버린 판정은 이 안내의 잘못이다.
6. 받아들인 어긋남은 번호가 아니라 지문으로 알아본다.
7. 보안 지적은 묶어 넘길 수 없고, 받아들이려면 도하가 이유를 글로 쓴다.
8. 문장은 설계 문서에서 그대로 옮긴다. 바꿔 쓰지 않는다.
9. 코드를 고치지 않는다. 커밋하지 않는다.
