# second-brain

> 판: 2026-10-17 · 원본: GitHub `tthwaghtt/second_brain`(비공개; 레포 이름이 바뀌면 이 줄과 9·10장만 고침)
> 이 스킬은 second_brain 노트를 **컴파일한 결과**입니다. 원본 노트를 통째로 읽지 않습니다. 규칙이 모자랄 때만 9장대로 원본의 장 하나를 엽니다.
> 이 규칙과 프로젝트의 CLAUDE.md·사용자 지시가 부딪히면 **사용자 지시가 이깁니다.** 프로젝트에 맞지 않는 규칙은 그대로 복사하지 말고 빼거나 바꾼 뒤, 이유를 보고합니다.

## 1. 프로젝트에 적용할 때 (시작·정리 공통)

1. **먼저 읽기만 합니다.** 그 프로젝트의 규칙 파일, 상태 문서, 폴더 구조를 보고 이 스킬과 어긋나는 곳을 표로 보고합니다(문제 / 어긋난 규칙 / 고칠 안). 고치기 전에 승인을 받습니다.
2. **크기에 맞게 만듭니다.**
   - 작음(세션 몇 개): `CLAUDE.md`(짧게) + `HANDOFF.md`
   - 중간: + 사용자 원문 기록 + 설계 문서 하나
   - 큼(세션 수십 개): + 문서 폴더 나누기, 로드맵, 상태 문서, 코드 지도와 문서 검사
   - 처음부터 큰 틀을 만들지 않습니다. 커지면 그때 나눕니다.
3. **첫 세션에 사용자에게 물을 것:** 목적과 1순위 기준, 보고 언어, 승인 지점(무엇은 묻고 무엇은 바로 하나), 건드리면 안 되는 파일, 비밀(키)의 위치, 세션 단위.
4. **처음부터 지킬 습관:** 한 사실은 한 곳 · 장 번호와 "파일 + 장" 참조 · 겹치지 않는 문서 이름 · 규칙 파일 200줄 이하 · 계획의 숫자는 코드로 확인하고 추정은 "추정"으로 표시 · 세션 끝마다 상태 문서 + 커밋 + inbox 한 줄.

근거: `playbooks/new-project-kickoff.md`

## 2. 문서 구조

- **한 사실은 기준 문서 한 곳에만 둡니다.** 다른 문서는 "파일 + 장"으로 가리키기만 합니다.
- **문서는 고치는 법으로 네 종류로 나눕니다.** 한 문서에 종류를 섞지 않습니다.

| 종류 | 고치는 법 | 예 |
|---|---|---|
| 흐름 | 매번 덮어씀 | 상태 문서(STATUS, HANDOFF) |
| 기준 | 고쳐 쓰고 바뀐 날짜를 적음 | 설계, PRD |
| 기록 | 끝에 덧붙이기만 | 사용자 원문, 결정 기록 |
| 보고서 | 그날 결과로 얼림, 틀리면 머리에 정정 메모 | 조사·점검 보고서 |

- **규칙 파일(CLAUDE.md)** 에는 지금 단계, 늘 지킬 원칙, "일 → 문서의 장 → 코드" 찾아가기 표만 둡니다. 200줄 아래. 사람만 볼 메모는 `<!-- -->` 주석으로 씁니다(Claude에게 실리지 않음).
- **옛 판, 보관, 백업은 읽는 길에서 뺍니다.** 규칙 파일에 "따르지 말 것"이라고 표시합니다.
- **초안과 확정을 구분합니다.** 새 설계 문서 머리에 "초안, 승인 전"을 두고, 사용자에게 물을 것은 문서 끝 "정할 것"에 모읍니다.

근거: `insights/doc-structure.md`, `insights/context-consistency.md` 2장

## 3. 결정이 바뀔 때

1. 사용자 원문을 날짜와 함께 원문 기록에 덧붙입니다.
2. 기준 문서를 고칩니다. 옛 결정은 지우지 않고 `~~취소선~~ → 새 결정(날짜)`으로 남깁니다.
3. **그 낱말·숫자로 프로젝트 전체를 검색합니다.** 복사본은 가리키기로 바꾸고, 그 결정을 기다리던 문구("적용 대기", "사용자가 정함")는 지웁니다. 가장 자주 놓치는 단계입니다.
4. 다음 세션 시작 프롬프트에 영향이 있으면 고칩니다.
5. 보고에 "바꾼 곳 / 그대로 둔 곳(왜)"을 적습니다.

근거: `insights/context-consistency.md` 3·4·9장

## 4. 세션 운영과 인수인계

- **한 세션 = 한 목표.** 새 세션으로 넘어가는 때: 목표를 끝냈을 때, 압축이 두 번째일 때, 결정을 잘못 기억하는 일이 보일 때, 1시간 넘게 쉰 뒤.
- **상태 문서는 하나만(STATUS.md 또는 HANDOFF.md):** Goal / Current state / Active files / Changes made / Failed attempts / Specific next step + 다음 세션 시작 프롬프트 하나.
- **시작 프롬프트 규칙:**
  - 미래 세션 것을 미리 쓰지 않습니다. 다음 하나만, 상태 문서 한 곳에 둡니다.
  - 머리에 작성 날짜, 작성한 세션, 다음 세션 번호, 승인 원문의 출처를 적습니다. 승인 문구를 지어내지 않습니다.
  - 다음 할 일이 정해지거나 바뀔 때마다 고칩니다(세션이 갑자기 끊겨도 맞는 프롬프트가 남게).
  - "시작 전에 이해한 계획을 짧게 보고해"를 넣습니다.
- **로드맵에는** 세션마다 전제, 목표, 읽을 것(장 단위), 할 일, 멈출 곳만 둡니다.
- **새 세션이 읽는 순서:** 규칙 파일(자동) → 상태 문서의 "지금" → 그 세션의 "읽을 것" 장만.
- **닫기 전:** 원문 기록 → 기준 문서 → 상태 문서 새로 쓰기 → 검사(있으면) → 커밋 → 사용자에게 다음 프롬프트 알림 → second_brain inbox 한 줄(10장).

근거: `playbooks/handoff.md`, `insights/context-hygiene.md`

## 5. 파일·폴더 옮기기

1. 계획(옮길 자리 그림, 깨질 수 있는 곳, 확인 방법)을 먼저 보고하고 승인을 받습니다.
2. 누가 부르는지 조사합니다: `grep -rl 파일이름`, 위치 계산 식(`ROOT = …parent…`), import, 예약 작업.
3. 지금 상태를 커밋합니다. 옮기는 중엔 `git stash`를 쓰지 않습니다(이름 바꾸기가 풀림).
4. `git mv`로 옮깁니다.
5. 경로를 고칩니다. 문자열 일괄 치환에 더해 **조각 경로**(`"scripts" / "x.py"`, `join(ROOT, "scripts", …)`)도 검색합니다. 사용자 원문 인용 속 경로는 바꾸지 않습니다.
6. **실제로 실행해 확인합니다:** `py_compile`, `--help`, 주요 도구 한 번, 문서 참조 검사.
7. 지도(규칙 파일의 표, README, 코드 지도)를 고치고, 모순을 점검하고, 커밋합니다.

근거: `playbooks/reorganize-folders.md`, `lessons/mistakes.md` 7~10

## 6. 탐색 대신 지도

- 문서는 **장 단위로 통째로** 읽습니다(잘라 읽다 빠뜨리지 않게). 코드는 지도의 줄 번호 근처만 읽습니다.
- **코드 프로젝트(파일이 수십 개 이상)는 Graphify로 코드 지도를 만듭니다.**
  - `uv tool install graphifyy`(y 두 개) → `graphify install --project` → `/graphify .` → `graphify query "…"`, `graphify path A B`, `graphify explain X`
  - `graphify hook install`로 커밋마다 그래프를 갱신합니다.
  - 코드만이면 LLM 토큰 0입니다. 문서까지 넣으면 토큰이 들고 설정된 외부 API로 보냅니다. 민감하면 `--code-only` 또는 `GRAPHIFY_BACKEND=none`.
  - `INFERRED` 선은 원본 코드로 확인합니다. 파일 몇 개짜리 프로젝트에는 쓰지 않습니다.
  - 근거는 외부 문서뿐이고 아직 실제로 써 보지 않았습니다. 처음 쓰면 결과를 inbox에 남깁니다.

근거: `insights/file-index-tools.md`, `점검.md` 6장

## 7. 토큰 습관

- 가장 큰 비용은 긴 세션의 다시 읽기입니다. 세션을 짧게 끊고, 오래 쉰 뒤엔 새 세션을 엽니다. 이어 갈 필요가 없으면 `/compact`보다 새 세션이 쌉니다.
- 큰 출력은 `tail`·`grep`으로 받고, 이미지는 여러 장을 한 시트로 봅니다. `node_modules`, 빌드·렌더 출력 폴더는 열지 않습니다.
- 별도 세션(하위 에이전트)은 끝날 때 원래 세션을 대화 전체째 깨웁니다. 꼭 필요할 때만 씁니다.
- 앱에서 연결(MCP)을 끄면 전역 기본값이 바뀝니다. 끄기 전에 사용자에게 알립니다.

근거: `insights/token-economy.md`

## 8. 확인 습관 (삽질에서)

- 계획과 문서의 숫자, 좌표와 각도의 부호는 그 코드의 규칙을 읽고 **실행해서** 확인합니다. 같은 값을 여러 문서에 따로 쓰지 않습니다.
- 외부 사실(라이선스, 별 수, 파일 경로, 기능)은 원본에서 따로 확인합니다. "직접 확인"이라 적힌 조사서도 틀릴 수 있습니다.
- 검사 도구는 일부러 망가뜨린 사본으로 시험합니다.
- 큰 작업은 끝나면 바로 커밋합니다.

근거: `lessons/mistakes.md`

## 9. 더 자세히 필요할 때 (원본 열기)

이 스킬의 규칙으로 모자랄 때만 엽니다.

1. second_brain 레포를 세션에 붙입니다(`tthwaghtt/second_brain`, 비공개).
2. `INDEX.md`만 먼저 읽습니다.
3. 위 근거 꼬리표의 노트에서 **장 하나만** 꺼냅니다: `python3 tools/doc_section.py <노트> <장>`
4. 노트 전체, 저장소 전체, `inbox/`는 읽지 않습니다.

## 10. 세션 끝: second_brain에 되돌려 쓰기

- 이번 세션에서 **다른 프로젝트에도 통할 교훈**이 있을 때만 한 줄 남깁니다. 없으면 쓰지 않습니다.
- 프로젝트에만 해당하는 사실(숫자, 파일 이름)은 쓰지 않고 일반화한 교훈으로 씁니다. 비밀, 개인정보, 고객 정보는 쓰지 않습니다.
- **second_brain 레포가 push 가능하게 붙어 있으면**, 그 clone에서:
  ```bash
  python3 tools/add_note.py inbox --source "<프로젝트>/<세션>" --scope "<적용 범위>" \
      --what "<무엇>" --why "<왜>" --next "<다음엔>"
  git add inbox && git commit -m "inbox: <프로젝트> <한 줄 요약>" && git push
  ```
- **붙어 있지 않으면** 같은 내용을 세션 끝 보고에 "second_brain inbox에 남길 한 줄"로 적어 사용자에게 줍니다.
- `insights/`, `lessons/`, `playbooks/`, 이 스킬은 직접 고치지 않습니다. 그건 사용자가 요청한 컴파일 세션의 일입니다.
