# 예시: 어려운 글 → 쉬운 글

> plain-words 스킬의 참고 글. 필요한 장만 엽니다. 어려운 글은 원문 구역으로 감싸 두었습니다(검사가 세지 않게, 6번 예처럼).

## 1. 번호와 만든 말이 겹친 문장 (정답지 페이지)

<!-- 원문 -->
어려운 글: 다름 칸(K2, K4, K5) 가운데 K2에 기댄 G1과 K4에 기댄 G2가 모두 약해짐이라 남은 가설은 있으나 살아남음은 없다.
<!-- /원문 -->

쉬운 글: 보통 영상과 다른 점은 세 군데(첫 장면, 편집, 소리)였어요. 첫 장면을 근거로 세운 첫 번째 짐작과, 편집을 근거로 세운 두 번째 짐작을 댓글로 확인해 보니 둘 다 근거가 약했어요. 둘 다 버리지는 않았지만, 확인된 짐작은 아직 없어요.

고친 점: 번호는 가리키는 내용으로(보통 영상과 견준 표의 2번 줄 = 첫 장면, 4번 = 편집, 5번 = 소리), 만든 말은 용어집 뜻으로(근거가 약함, 버리지 않은 짐작, 확인됨), 한 문장은 세 문장으로.

## 2. 숫자의 뜻을 모를 때 (원인 보고서 예)

<!-- 원문 -->
어려운 글: 다름 칸 K2에 기댄 G1이 시간표(0.91)로 약해진 채 남았고
<!-- /원문 -->

쉬운 글: 첫 장면이 보통 영상과 다르다는 점을 근거로 세운 첫 번째 짐작은, 관찰 시간표(영상을 구간마다 적은 표)를 보니 근거가 약해졌어요. 시간표에서 나온 값 0.91이 무엇을 잰 것인지는 아직 확인하지 못했어요.

고친 점: 모르는 숫자의 뜻을 지어내지 않고, 확인하지 못했다고 밝혔습니다.

## 3. 칸 이름이 든 문장 (보고서)

<!-- 원문 -->
어려운 글: no_special_reason이 true인 편은 card_summary를 비우고 recsql로 표에 넣는다.
<!-- /원문 -->

쉬운 글: 영상 안에서 터진 이유를 못 찾은 편은 카드용 요약을 비워 두고, 승인한 추천을 넣는 명령문으로 추천 표에 넣어요.

이름을 꼭 남길 때: 카드용 요약 칸(`card_summary`)은 비워 둬요. (뜻이 먼저, 이름은 뒤 백틱 안)

## 4. 세션 사이 메모와 새 세션 첫 지시문

<!-- 원문 -->
어려운 글: S5b 결과 받으면 S5a가 recsql 돌려서 daily_recs에 넣고 STATUS 4장 갱신.
<!-- /원문 -->

쉬운 글: 깊은 분석 세션이 결과를 내면, 매일 추천 세션이 승인한 추천을 추천 표(`daily_recs`)에 넣어요. 넣는 명령문은 매일 도구가 만들어요. 그다음 상태 문서의 "다음 할 일"을 고쳐요.

왜 중요한가: 받은 세션은 첫 지시문의 말투를 이어받습니다. 지시문이 암호면 그 세션이 도하에게 쓰는 글도 암호가 됩니다.

## 5. 질문 하나를 다섯 칸으로

**질문: 보내는 글은 보내기 전에 한 번 멈출까요?**
- **배경:** 앞 단계에서 "저장은 막지 않고 경고만"으로 정했어요. 그런데 보내는 글은 경고가 보낸 뒤에 오면 이미 도착한 뒤예요.
- **무엇인지:** 마무리 상자, 세션 메시지, 새 세션 첫 지시문을 보내기 직전에 한 번만 멈추고, 고칠 낱말을 알려 줘요. 몇 분 안에 다시 보내면 그대로 나가요.
- **왜 필요한지:** 새 세션 첫 지시문은 되돌릴 수 없고, 받은 세션이 그 말투를 이어받아요.
- **도하가 할 일:** A나 B를 골라 주세요. 정해야 만들 수 있어요.
- **답에 따라:** A면 보내는 글 세 가지만 한 번 멈춰요. B면 모두 보낸 뒤 경고만 해서, 어려운 글을 도하가 먼저 받게 돼요. 추천은 A예요. 도하가 읽는 글이 도착하기 전에 고쳐지는 방법이라서요.

## 6. 기계 원문 감싸기

마크다운:

```markdown
**요약:** 첫 장면이 보통 영상과 달랐고, 그 점을 근거로 세운 짐작은 근거가 약했어요.

<!-- 원문 -->
| 칸 | 값 |
|---|---|
| based_on | K2 |
| verdict | 약해짐 |
<!-- /원문 -->
```

페이지(HTML):

```html
<p><b>요약:</b> 첫 장면이 보통 영상과 달랐고, 그 점을 근거로 세운 짐작은 근거가 약했어요.</p>
<details><summary>원문(분석표) 보기</summary>
  <pre>based_on: K2 · verdict: 약해짐</pre>
</details>
<div class="quote" data-raw>도하가 쓴 말을 그대로 옮긴 칸</div>
```

## 7. 새 AI에게 읽히기 (시킬 말)

앞 대화를 모르는 서브에이전트(중간 크기 모델이면 충분)에게 아래처럼 시킵니다. 고칠 곳만 받고, 고치는 일은 쓴 쪽이 합니다.

```
너는 '도하'라는 대학생이다. 개발 초보이고, 이 글을 앞뒤 맥락 없이 처음 읽는다.
아래 파일 하나만 읽어라. 다른 파일은 열지 마라. 파일: <경로>
막히는 곳을 중요한 순서로 적어 줘:
1) 풀이 없이 나온 낱말  2) 무엇을 가리키는지 모르는 말(그것, 3장, 파일 이름)
3) 왜 필요한지나 도하가 할 일을 알 수 없는 곳  4) 앞뒤가 안 맞는 숫자·날짜
5) 고를 때 필요한데 빠진 정보
항목마다: 원문 문장(짧게) / 왜 막히는지 / 고칠 제안 한 줄.
끝에 "이 글만 읽고 판단할 수 있나"를 한 줄로. 파일은 고치지 마라.
```

## 8. 자주 하는 실수

| 실수 | 고친 모양 |
|---|---|
| 이름을 앞에, 뜻을 괄호에 | "첫 장면(K2)" (뜻이 먼저) |
| 문서의 장 번호로 가리키기 | "결정 문서의 '이미 정한 것'" (필요하면 뒤 괄호에 장 번호) |
| 세션 이름으로 일 나누기 | "경쟁사 세션 몫" |
| 영어 칸 이름을 문장에 섞기 | "특별한 이유 없음으로 판정된 편" |
| 모르는 숫자를 그럴듯하게 풀기 | "이 값이 무엇인지는 아직 확인하지 못했어요" |
| 경고를 피하려고 괄호·백틱으로만 감싸기 | 뜻으로 바꿔 쓰기. 감싸기는 이름이 꼭 필요할 때만 |
| 다섯 칸을 채우려고 시간·결과를 짐작하기 | 원문에 있는 것만. 모르면 "확인하지 못했어요" |
| 모든 세부를 시간순으로 늘어놓기 | 된 일 / 남은 일 / 도하가 할 일로 묶고, 나머지는 보고서로 가리키기 |
